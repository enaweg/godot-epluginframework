# Plugin state files

The framework creates `res://addons/eplugin-state.json` from the currently active plugins (ePlugin-managed and plain Godot plugins) if the file is missing. Commit this file with the addon files. It records the last acknowledged plugin versions and completed activation or deactivation states, including ePlugin Framework itself.

The first snapshot is a baseline of the editor's current state; it cannot recover versions installed before the file existed. Later edits to `plugin.cfg` do not advance the acknowledged version until a migration or update completes. The recorded state of plain GDScript and C# plugins is refreshed at startup and before manual retry; toggling them in **Project Settings > Plugins** is noticed on the next frame, which handles their licenses, dependants and optional recipes. Later consumers refresh the index before use. Startup discrepancies are reported without overwriting existing entries, and enabled plugins missing from the index are added. Entries remain after disabling or removing a plugin. If a version is missing, the plugin gets a local invalid record; repair `plugin.cfg` and use **Retry failed** in the [ePlugin Manager](eplugin-manager.md). A [GDExtension without `plugin.cfg`](gdextension-plugins.md#gdextensions-without-plugincfg) has no version in its files: the file records one only after ePlugin installed a version of it, and until then its version is unknown.

The file changes only when its content does: enabling or disabling a plugin that is already recorded in that state leaves it untouched. Its `lastCompletedAttemptId` names the last update that was acknowledged, which recovery uses; enabling and disabling plugins do not change it, so teammates toggling different plugins do not conflict on it. (Version 0.9.0 also set it for every toggle, so after upgrading it can name such a toggle until the next update; that is harmless.) Framework versions after 0.9.0 read fields that a newer version added and keep them when they write the file again; 0.9.0 refuses such fields, but no version writes any yet, so 0.9.0 and later versions read each other's files, also when a framework update is rolled back. A file with another `schemaVersion`, or without its `plugins` list, is never overwritten: the plugin state stays read-only until the file is repaired or the framework is updated.

The adjacent `res://addons/eplugin-state.json.user` stores unfinished or failed work on one machine. Add `addons/eplugin-state.json.user` to the project's `.gitignore`. An unresolved entry blocks automatic recipe retry after an editor restart or assembly reload. After fixing the cause and any partial side effects, use **Retry failed** in the [ePlugin Manager](eplugin-manager.md) to retry explicitly.

The file also records accepted plugin licenses in its `licenses` list. The list is left out until a license is accepted, so the file stays readable by framework versions without license support. See [Plugin licenses](plugin-licenses.md#recorded-acceptances). Likewise, its `welcomes` list records the plugins whose welcome page was shown, and is left out until one was; see [Plugin welcome pages](plugin-welcome.md#recorded-welcome-pages).

A failed operation leaves the checked-in JSON at its last completed state. These files provide the basis for migration and rollback tooling; they do not restore addon files or undo partial recipe changes themselves. Update journals and recovery steps are covered in [Updating plugins](updating-plugins.md#builds-restart-and-recovery).
