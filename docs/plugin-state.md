# Plugin state files

The framework creates `res://addons/eplugin-state.json` from the currently active plugins (ePlugin-managed and plain Godot plugins) if the file is missing. Commit this file with the addon files. It records the last acknowledged plugin versions and completed activation or deactivation states, including ePlugin Framework itself.

The first snapshot is a baseline of the editor's current state; it cannot recover versions installed before the file existed. Later edits to `plugin.cfg` do not advance the acknowledged version until a migration or update completes. The recorded state of plain GDScript and C# plugins is refreshed at startup, when the ePlugin Manager lists the plugins, before update checks and installations, and before **Retry** or **Disable**; toggling them in **Project Settings > Plugins** is noticed on the next frame, which handles their licenses, dependants and optional recipes. Startup discrepancies are reported without overwriting existing entries, and enabled plugins missing from the index are added. Entries remain after disabling a plugin. A plugin recorded as activated whose folder was removed while the editor was closed (no `plugin.cfg`, and no GDExtension add-on in its place) is forgotten like Godot forgets it: the first editor start that finds it missing marks its entry with `"missing": true`, and the next start (on any machine, once the file is committed) removes the entry if the plugin is still missing; its accepted license and shown welcome page stay recorded. A plugin that turns up again in between loses the mark, and one with unfinished work in the `.user` file or an update is left alone. Entries of disabled plugins remain after their folder is removed. If a version is missing, the plugin gets a local invalid record; repair `plugin.cfg` and use **Retry** under [Needs attention](eplugin-manager.md#needs-attention) in the ePlugin Manager. A [GDExtension without `plugin.cfg`](gdextension-plugins.md#gdextensions-without-plugincfg) has no version in its files: the file records one only after ePlugin installed a version of it, and until then its version is unknown.

The file changes only when its content does: enabling or disabling a plugin that is already recorded in that state leaves it untouched. Its `lastCompletedAttemptId` names the last update that was acknowledged, which recovery uses; enabling and disabling plugins do not change it, so teammates toggling different plugins do not conflict on it. (Version 0.9.0 also set it for every toggle, so after upgrading it can name such a toggle until the next update; that is harmless.) Updating the framework never loses the recorded state: every version reads the files of the versions before it. A version also reads a file that a newer version wrote, skipping the fields it does not know, and writes only the fields it knows: after going back to an older framework version, state that only the newer version knows is lost once the older version writes the file. A file with another `schemaVersion`, without its `plugins` list, or with invalid or duplicate entries, is never overwritten, and neither is it while the `.user` file below is such a file: the plugin state stays read-only until the file is repaired or the framework is updated. When the file changes on disk while the editor runs, for example by a `git pull`, the framework reads it again before it writes and keeps the other entries. It refuses to write only when the file was deleted, cannot be read (e.g. an unresolved merge conflict) or changed an entry the write sets too, to another value, such as the state of the plugin just toggled; that plugin then needs attention. The framework then holds the file as it is on disk, so **Retry** builds on the teammate's change (for example the version their update recorded) instead of conflicting again. A plain plugin whose write failed is also written again as soon as the file can be written, without another toggle. A teammate's change that the write would make anyway, such as enabling the same plugin in the same version, does not conflict. Licenses accepted and welcome pages shown while the file cannot be written still count for the session, also after the file is read again and after C# assembly reloads, and the next write that succeeds saves them.

The adjacent `res://addons/eplugin-state.json.user` stores unfinished or failed work on one machine. Add `addons/eplugin-state.json.user` to the project's `.gitignore`. An unresolved entry blocks automatic recipe retry after an editor restart or assembly reload. After fixing the cause and any partial side effects, use **Retry** in the [ePlugin Manager](eplugin-manager.md)'s [Needs attention](eplugin-manager.md#needs-attention) dialog to retry explicitly, or **Disable** to give up on enabling the plugin.

The file also records accepted plugin licenses in its `licenses` list. The list is left out until a license is accepted. See [Plugin licenses](plugin-licenses.md#recorded-acceptances). Likewise, its `welcomes` list records the plugins whose welcome page was shown, and is left out until one was; see [Plugin welcome pages](plugin-welcome.md#recorded-welcome-pages).

A failed operation leaves the checked-in JSON at its last completed state. These files provide the basis for migration and rollback tooling; they do not restore addon files or undo partial recipe changes themselves. Update journals and recovery steps are covered in [Updating plugins](updating-plugins.md#builds-restart-and-recovery).
